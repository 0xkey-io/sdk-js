# C5 trusted OAuth v3 issuance and claim: default-closed implementation plan

> Review candidate only. This plan changes no product path or gate. Execute each slice in its owning repository under its local rules; preserve the dirty worktrees and existing V2 behavior. No staging, device, release, or readiness claim follows from source tests.

## Goal and boundary

An OAuth v3 session is usable only when a fresh, original request is bound to an authenticated classified Prepare, the **latest committed active** signed Auth Proxy config and parent/child authorization, a Signer-issued v3 JWT, and the exact Web pending claim or native host grant. Every missing, stale, conflicting, or unverified input fails closed. The dependency is **Go classified Prepare → Coordinator → Registrar latest signed config → Signer v3 → SDK Web / RN host grant**. A step may add RED tests before its dependency is implemented, but cannot mark itself GREEN by copying self-reported fields.

The current Web opt-in verifies a fixed production Signer signature, finite expiry, and local key possession, yet `C5_TARGET_CLAIM_RED=1` accepts a correctly signed JWT without parent/config/purpose/nonce. Existing Signer OAuth JWTs do not carry those fields. Services classified Prepare returns 503 for `Prepared`; the old OAuth handler and 30-second legacy config cache cannot authorize v3. Registrar's `active_view_v2` proves a signed snapshot relative to a row, not latest committed currentness. RN Expo is a disconnected source candidate with no trusted host enrollment, protected signing key, or signout lifecycle. These are the starting RED facts, not partial acceptance.

**2026-09-30 source supersession:** The preceding `C5_TARGET_CLAIM_RED=1` acceptance is a historical pre-fix RED. The private Web opt-in now rejects signed v3 JWTs with missing or mismatched target fields on first claim and cold recovery; its test Signer and target profile are harness-only, while the product trust profile remains `undefined`. This is a local deny gate, not trusted server issuance. Existing Signer OAuth JWTs still lack v3 claims, Services `Prepared` login still returns 503, and the common revocation order, one-use issuer ledger, online currentness, and reviewed staging build pin remain open. Default Core and G5/G6 remain closed; the other server-side RED facts above still apply.

### Contract to freeze before implementation

Create one cross-language fixture set for a **new, explicitly versioned** OAuth session contract. The v3 JWT must carry strict `session_version=3`, `session_purpose="bound-oauth-session-v3"`, `parent_organization_id`, `auth_proxy_config_id`, `config_generation`, `config_revision`, `config_digest`, `operation_nonce`, `deployment_audience`, and the existing child `organization_id`, `user_id`, `public_key`, `iat`, finite `exp`, and `jti`. Exact spelling, encoding, types, canonical URL/audience mapping, and domain-separated operation signature bytes must be frozen in fixtures before code. Suggested encodings are base64url for fixed-size generation/digest/nonce and decimal string for revision; reject aliases and noncanonical forms. The audience comes from a reviewed deployment trust profile, not a page-supplied URL. The signed parent is distinct from the child organization in the session.

The operation nonce must originate in a pending Web or native-host operation and be proven together with the target, purpose, and public key by a holder P-256 signature over canonical, domain-separated bytes. An unsigned nonce forwarded from JSON is only an echo. Client claim/host grant consumes it once, **and server issuance needs its own durable one-use ledger**. The holder proof and strict OIDC provider proof must authenticate one canonical operation transcript across Prepare and Execute/Signer calls: operation ID, nonce, parent/config selector, child target, audience, purpose, public key, original stamped request digest, and provider proof digest/verified issuer-subject binding. A bearer OIDC token and a separately valid holder signature are insufficient if they can be swapped between operations. The server ledger must atomically bind the verified transcript, status, and reserved `jti`; same-ID/same-digest retry may return the same signed result and `jti`, while changed digest/proof or a second `jti` is rejected. If exact response replay cannot be safely retained, a lost-response retry denies and requires a fresh operation; it must not mint another `jti` for the old one. Do not store raw OIDC tokens in the ledger or logs. Define the signed request/stamp verification chain and ledger transaction in Go/Coordinator fixtures; never infer it from an HTTP client's apparent caller or response.

Use a fixed, reviewed Notarizer verification pin for signed config and parent evidence and a fixed, reviewed Signer verification pin for session JWTs. A staging bundle or host build must receive its staging pins through a trusted build/deployment channel. JWT `kid`, Auth Proxy responses, runtime SDK config, and browser storage cannot add a trust root. Rotation requires a separately authorized, pinned keyset transition and old/new overlap tests. No dynamic pin fetch is part of this plan.

### Unresolved authority decisions: hard gates, not implementation assumptions

1. **One issuance/revocation order.** Specify the authoritative committed rows and one deterministic linearization point shared by OAuth v3 issuance, config disable/revision, and parent-child unlink/reparent/revocation. A candidate is a committed `jti` issuance authorization under ordered config-head and parent-child-head locks; both revocation writers take the same locks, and every later use checks those heads against the issuance record. Signer cryptographic signing after that commit cannot itself confer current authority: a concurrent later revocation makes the JWT unusable even if its signature completes. If the config head, parent-child head, and issuance ledger cannot participate in one serializable authority or a reviewed equivalent fencing protocol, **do not issue usable v3 sessions**. A historical signed snapshot or an RPC-time read is not a linearization point. Freeze exact lock order, commit order, timeout/ambiguous-commit behavior, and the final API-use check before GREEN.
2. **Two-call proof and replay ledger.** Freeze the canonical operation transcript, provider proof representation, authenticated hop identities, ledger owner/retention, and same-`jti` response replay contract before adding a v3 Signer path. No independently verified OIDC/holder pair may be joined by a caller-supplied operation ID alone. A prepared operation cannot be repurposed for another OIDC subject, parent, config, key, nonce, or audience.
3. **Online currentness at use.** Identify the authoritative Services introspection/admission endpoint and its authenticated response format for exact `(jti, child, parent, config generation/revision/digest, audience, current parent-child head)`; define no-cache and failure behavior. Web and native local checks are not final authority because revocation can commit between check and signing. The receiving service must enforce the same current-selector/parent-child/jti fence at the sensitive API request's admission point. Until this endpoint and server check exist, getters, stamping, native signing, and transport remain v3-disabled; offline, timeout, stale, and unverifiable responses deny.
4. **Trusted build profiles.** Freeze an independently reviewable staging and production manifest mapping Signer and Notarizer pins, exact deployment audience/API/Auth Proxy origins, config trust profile, SDK package and browser bundle digests, Enclave/service image or measurement identities, and native build identity. Record iOS bundle ID, Team ID/signing certificate and native module digest, plus Android application ID, signing certificate SHA-256 and native module digest. Specify who signs/approves the manifest and how immutable values enter Web bundles and native binaries; no runtime response, JWT header, app JS config, or self-reported native constant may select a pin/audience. The current source has only the production Signer constant and no reviewed staging profile or built app proof. If an existing trusted release authority cannot attest this mapping, staging/prod v3 remains closed rather than inventing a new policy here.

## 1. Go: classified Prepare and original OAuth request

**Owning files:** Services `go/internal/authproxy/server.go`, `go/internal/authproxy/middleware/account_config_lookup.go`, `go/internal/authproxy/handler/oauth.go`, `go/internal/authproxy/handler/proxy_handler.go`, and focused `*_test.go` beside them. The old `go/internal/authproxy/store/proxy_config.go`, `grpc_config_repo.go`, and `go/internal/authproxy/proxy/stamper.go` remain legacy inputs only.

**RED:** Add a disabled-v3 route test in which an authenticated `Prepared` decision, original stamped request, holder operation signature, and target are supplied. Today it returns 503. Add negative cases for absent/invalid original stamp, changed body after stamp, wrong parent/config/purpose/nonce/public key, reused nonce with different request digest, untrusted request hints, and a valid legacy cache entry without Prepare. Add a two-call swap: Prepare with holder A/key A, then Execute with holder B or with subject B's OIDC proof in place of the proof bound to A's operation, using the same caller-supplied operation ID; no Coordinator v3 admission may result. Each failure must occur before Signer invocation. Assert old LegacyPayload `/v1/oauth_login` request and flat `{session}` response remain byte-compatible.

**GREEN:** Add a dedicated adopted-v3 branch after the *same authenticated* classified Prepare. Pass a typed evidence envelope carrying the original verified request digest/stamp identity, verified holder signature, fresh operation nonce, Prepare's account/config selector, provider-proof digest, and trusted deployment profile to Coordinator. The two calls must use one authenticated, server-issued operation identity and the same canonical transcript; a caller-supplied matching string is not proof. Do not assemble authority from the old OAuth JSON, old handler, proxy credential cache, or reconstructed request body. Fail closed if Prepare is absent, ambiguous, stale, or disabled. Keep the branch behind an explicit server-side v3 gate; default `NewServer` and existing handlers remain V2.

**Proof/compatibility gate:** A focused Go test must show a user can change every browser-supplied target hint without changing the typed trusted envelope, and that an altered original stamped request is rejected. Pin this hop to the authenticated service identity and explicit v3 route/contract version. Go GREEN only establishes provenance into Coordinator, not signed config currentness or a usable SDK session.

## 2. Coordinator: fail-closed OAuth v3 admission

**Owning files:** Services `services/coordinator/src/application/services/executors/auth.rs`, `services/coordinator/src/application/services/executor.rs`, related gRPC interface and focused tests under `services/coordinator/src/interfaces/grpc/` and `application/services/`.

**RED:** Construct tests for an adopted-v3 request with missing authenticated Prepare, wrong account selector, replay/conflicting operation nonce, child under another parent, missing OIDC Fetcher/provider verification, claims-only/dev fallback, mismatched public key, and a disabled/revised config observed between admission and issuance. Add interleavings where holder A's Prepare is completed with B's OIDC proof, A's verified provider proof is completed with B's holder key, a lost response is retried with identical bytes, and a retry changes one transcript field. Assert at most one reserved `jti`, exact same-`jti` result or denial on identical retry, no second Signer request on conflict, and no issuance after a committed parent/config revocation. Test that profile sessions, internal X/Discord paths without their own strict proof, OTP/signup, and legacy OAuth never enter this v3 branch by accident.

**GREEN:** Introduce a typed v3 admission variant, accept only authenticated Go provenance, verify the original holder-bound operation and strict external OIDC/provider proof, resolve signed parent Organization/Notarization evidence, and request a Registrar latest-active selector. Under the reviewed common authority transaction/fence, atomically consume the prepared transcript and reserve one `jti` against exact provider proof, holder key, original request, config head, and parent-child head. Carry that committed authorization identity and exact child organization, parent, config ID/generation/revision/digest, purpose, nonce, request digest, and trusted audience to Signer in a versioned intent. A race with disable/revision or parent-child unlink/reparent follows the single commit order: revocation first rejects issuance; issuance first is immediately invalidated for later use by revocation. No Fetcher/fallback means reject for v3 while legacy behavior remains explicitly scoped. If the Services authority cannot establish this order across its current databases, leave the branch refusing v3 and complete the unresolved authority design gate.

**Proof/compatibility gate:** Verify service-authenticated Go→Coordinator transport and exact provenance types; no generic `ExecuteRequest` extension that accepts caller-filled v3 strings. The trust pin is the established service identity plus Notarizer pin for parent/config evidence, not a request header. Test the durable operation ledger with unique operation ID and unique `jti`, exact retry fingerprint, conflicting retry rejection, crash/ambiguous-commit recovery, and no raw OIDC token persistence. Isolated PostgreSQL 16 tests need two real transactions with barriers: issuance wins then disable/unlink wins; disable/unlink wins then issuance must fail; and revision/disable/re-enable or reparent to the old apparent target cannot resurrect the old authorization. Source-only mocks do not close this race.

## 3. Registrar: latest committed, active signed config

**Owning files:** Services `services/registrar/src/application/services/auth_proxy_config_reader.rs`, `auth_proxy_account_runtime.rs`, signed projection/reader tests under `services/registrar/src/application/services/auth_proxy_projection_evidence/tests/`, and the existing signed config evidence verifier in Enclave `crates/protocol/src/auth_proxy_config_evidence.rs` where the cross-repository contract requires it.

**RED:** Show that a valid historical `active_view_v2` can coexist with a newer committed disabled/revoked/revised selector; a signed old snapshot alone must not authorize v3. Add deterministic tests for wrong account/config, generation/revision/digest mismatch, unpublished or unresolved projection, malformed signature, and signed parent mismatch. With two PostgreSQL 16 transactions, pause issuance after a latest read, commit disable/revision (and separately parent-child unlink/reparent), then resume it: the stale read must not authorize a usable `jti`. Reverse the lock order in a second schedule: a committed issuance can precede revocation, but every later use must reject after revocation commits. Disable→re-enable with a new generation must not revive an old JWT even when ID/parent strings match.

**GREEN:** Expose a dedicated Registrar read that verifies the signature/digest with the fixed Notarizer pin **and** proves it is the latest committed selector for that account/config under the documented ordering/lock rule. A typed snapshot/attestation is evidence for the common issuance authority transaction, not a substitute for its lock/fence. The authoritative config and parent-child revocation writers must participate in the same documented commit order, or a reviewed equivalent monotonic fence must be proven by the two-transaction tests. Include generation, revision, digest, enabled state, parent/child selector **and its own current head/version**, and proof identity in the result. Reject gaps, unresolved delivery/intent, ambiguity, and future enabled=true state until the C2 enabled policy is approved. Reuse `active_view_v2` only as a component after latestness is separately established. If Registrar cannot demonstrate current parent-child state or share revocation ordering, return failure rather than a seemingly complete v3 proof.

**Proof/compatibility gate:** Existing C2 signed config work is disabled-only. This slice may implement read/negative tests, but enabling v3 requires the separate C2 policy and deployment gates for an enabled active config. A fixed signed snapshot fixture proves authenticity; the PostgreSQL race proves currentness. Source-only SQLite/mock results cannot substitute for that race.

## 4. Signer: independently verified v3 issuance

**Owning files:** Enclave `crates/protocol/src/intent.rs`, `crates/protocol/src/auth_proxy_config_evidence.rs`, `apps/signer/src/service.rs`, and Signer focused tests there or in `apps/signer/src/auth_proxy_account_v2_tests.rs`. Freeze a language-neutral JWT/request fixture consumed by Go, Services Rust, Signer Rust, and SDK tests.

**RED:** Preserve the current test showing that caller-supplied v3 hints on an old OAuth activity are not signed. Add explicit v3 rejection tests for unverified parent→child relation, a historically valid relation or config head **without a matching pre-revocation committed issuance authorization**, wrong Notarizer/config digest, absent committed one-use authorization/`jti`, wrong/absent operation signature or nonce, arbitrary audience, claims-only OIDC, a second intent with the same operation and changed proof, and any field copied from self-reported hints. A revocation committed after a valid issuance authorization is instead tested as denial at use, even if signing finishes later. Assert that the ordinary JWT remains versionless/V2 and cannot accidentally satisfy a v3 verifier.

**GREEN:** Add a distinct v3 intent and signing branch. Reverify the signed config and parent/child Notarization with fixed pins and the committed one-use issuance authorization tied to the exact current-head versions, transcript digest, and reserved `jti`; verify purpose, request/holder/OIDC binding, exact public key, audience, and finite lifetime. Sign the frozen v3 claim set from those verified values only. For a same-operation retry, return the same `jti` and exact signed result from a protected idempotency record or deny; never mint a second usable token. Keep ordinary OAuth, profileSession, and legacy JWT signing on their existing route. If Signer cannot authenticate the Coordinator authorization or independently validate the Registrar/parent evidence to the frozen contract, reject. A Signer signature attests issuance facts, **not** that those facts remain current at a later API use.

**Proof/compatibility gate:** Rust JWT fixture tests verify byte-level claim schema and signature interoperability with the SDK verifier. Negative tests reject missing/extra aliases, invalid base64url, unbounded expiry, wrong signing key, cross-audience replay, changed same-`jti` transcript, and a stale parent-child head. The Signer and Notarizer pins are build/deployment constants or authenticated keysets; no token-controlled key selection. Match Signer image/measurement, key identity, issuer, and audience to the reviewed environment build manifest before staging. Source tests are not Enclave deployment or staging proof.

## 5. SDK Web: first claim, cold recovery, and default Core integration

**Owning files:** SDK-JS `packages/core/src/__storage__/web/session-jwt-signature.ts`, `session-jwt-pin.ts`, `bound-credential.ts`, `bound-oauth-experiment.ts`, `packages/core/src/__storage__/bound-session.ts`, `packages/core/src/__clients__/core.ts`, `packages/core/src/__generated__/sdk-client-base.ts` and HTTP transport/admission adapter, browser tests in `packages/core/src/__tests__/browser/web-bound-oauth-optin.cjs` and `mixed-core-bound.red.cjs`, plus the React provider tests when the default manager changes. The legacy `packages/core/src/__stampers__/api/web/stamper.ts` cannot sign on behalf of a v3 session.

**RED:** Keep `C5_TARGET_CLAIM_RED=1` as the signed-but-unbound fixture: first claim and cold tab must reject with no owner/key write. Add signed but wrong parent, config ID, generation, revision/digest, purpose, nonce, audience, child, key, expiry, and signer-pin cases; test public `Core.storeSession` and a mocked/replaced OAuth HTTP client, duplicate/replayed claim, owner retirement, cross-target cold recovery, and JWT mutation after local proof. After a successful claim, revoke/disable the config or unlink/reparent the child while the tab stays open; `Core.getSession`, `getAllSessions`, active-session getter, bound stamper `sign`/`stamp`, and generated HTTP transport must refuse before exposing/using v3 credentials. Repeat with an offline/timeout/stale authority response and with a revocation between local online check and API arrival. A valid V2 JWT must not be adopted as v3. The test signer remains harness-only and cannot enter the production bundle.

**GREEN:** Before the first IndexedDB write, verify full JWT signature under the trusted environment pin, finite expiry, exact canonical deployment audience and constructed target, child/parent/config claims, fixed purpose, and the pending operation nonce and public key. Recheck decisive state inside the atomic four-store claim transaction; consume the nonce once and bind token digest, owner, key, epoch/generation, and target. Cold recovery re-verifies signature/expiry/target, local private-key proof, and retirement fence, then obtains a fresh authenticated online current-selector/parent-child/`jti` decision before returning a usable session. Route **every** v3 getter and bound `sign`/`stamp` through that check with no offline or stale-cache success. The generated HTTP transport must check immediately before request construction and the receiving service must check again at request admission under the authoritative revocation order; a client check cannot close the check-to-use race or constrain raw JWT use outside the SDK. Browser URLs and runtime config may select only a trust profile compiled into the reviewed build, never create or modify one. If the online authority endpoint/server admission check is absent, do not expose v3 getters, signer, or transport.

**Proof/compatibility gate:** Preserve default Core V2 until manager, all getters, stamper, and transport switch atomically, IndexedDB schema migration/rollback is reviewed, all direct public session writes and React provider paths use the same boundary, and the mixed-Core RED suite is GREEN. Keep the Web opt-in private/disabled until then. Run focused real Chromium two-tab tests for revocation, authority outage, and revocation between check and server admission, plus Core/React tests and typecheck on the pinned SDK toolchain. Inspect the built browser bundle/package digest for the intended staging or production fixed pin/audience and absence of test signer; match it to the approved manifest. A local test Signer signature is not a staging pin; staging needs an actual Go→Signer issuance and current-use denial proof.

## 6. RN/Expo: host-issued native grant and protected use

**Owning files:** SDK-JS `examples/authentication/captcha-rn-expo/native-bound-context-capability.md`, `native-bound-context.ts`, `modules/oxkey-bound-context/ios/OxkeyBoundContextModule.swift`, `modules/oxkey-bound-context/android/src/main/java/*/OxkeyBoundContextModule.kt`, sample `App.tsx`, and `packages/core/src/__tests__/mobile-bound-session-capability-test.ts`. Exact Android package path must be checked before editing. Core/React Native adapter files under `packages/react-native-wallet-kit/src/` remain disconnected until the host contract is proved.

**RED:** Run the opt-in native regression that removes A's key, inserts B under a different key, then has stale A read the latest revision, `putSession(absent A, null, token-A)`, and `setActive` to resurrect A. Also test stale A attempting to clear B after target-B authorization, a JS-forged event, replay, changed JWT digest, wrong runtime/target, and signout followed by stale use. After a genuine host grant, disable/revise the config or unlink/reparent the child; native grant, read, `sign`/`stamp`, and HTTP use must reject online, including offline/timeout/stale authority and revocation between native check and server admission. Current source candidate fails at least the A-resurrection and host-signout path. A JS-readable revision or JS-mintable token is not an authorization grant.

**GREEN:** Define a native-only host authorization event after host-side validation of the Signer v3 JWT with a native fixed pin, exact host target, and fresh authenticated online current-selector/parent-child/`jti` decision. The native layer holds the private key and pending nonce; it issues a one-use grant binding target, owner, runtime, session key, exact token digest, purpose, and monotonically fenced operation generation. Consume the grant atomically under the native write lock with a durable global epoch and target fence. Host signout increments the global epoch and clears/retire state through a native-only call; changing targets revokes the prior target. Native read and key-use methods recheck online currentness on every v3 use; receiving service rechecks at API admission. Offline, timeout, stale, or unverifiable authority responses deny and never fall back to a previously granted context. Persist credentials in platform protected storage with native key use, never expose raw SQLite/Keychain rows or signing material to JS. Verify the host-only enrollment/signout methods are absent from the Expo JS method table and reflected constants. Do not use `compareExchange` or revision equality as the authority for insertion/replacement/removal.

**Proof/compatibility gate:** Keep the Expo sample and default RN adapter disconnected while the source contract is tested. Then require iOS and Android native builds with the reviewed build-profile pins/audience, recorded app IDs/signing identities and native module digests, a real host authorization/signout caller, device process-death and concurrent-runtime tests, protected-storage and key-use inspection, authority-offline/revocation tests, server admission test, and actual Go→Signer staging JWT handshake. Check compiled native method tables and release artifacts, not only Swift/Kotlin source or JS-reflected constants. `pnpm` typecheck, source parsing, and simulated native tests are source evidence only; they do not close G5/G6. No Expo Go-only result can prove native module behavior.

## Verification order and stop rules

1. Freeze the cross-language v3 fixture, operation ledger and common authority linearization protocol, online use-check endpoint, and trusted build-profile mapping. These four items are **open design gates** until their owners approve concrete interfaces and evidence; the candidates in this plan are not approved policy or implemented source. Run the existing SDK signed-but-unbound RED and Signer self-hint negative test unchanged; record exact output before code work.
2. Implement Go and Coordinator rejection contracts first, then Registrar latest-head/common ordering proof, then Signer v3, then SDK Web. For each slice: run the focused RED, make the smallest GREEN change, rerun focused and owning package tests, inspect diff, and request independent review. Preserve V2 tests at every step. A green signature fixture without the one-use ledger and common revocation order cannot advance the gate.
3. Run isolated PostgreSQL 16 **two-transaction** schedules for issuance versus config disable/revision and parent-child unlink/reparent in both commit orders, same-operation exact retry versus changed transcript, and disable→re-enable with an old JWT. Run authority-unavailable tests and a revocation between client check and server API admission. A mock read of the latest row or a client-side check alone cannot close these RED cases.
4. Only after the signed fixture and online authority checks pass end-to-end locally, run real Chromium multi-tab/mixed-Core tests. Keep default Web closed until its migration and provider gates are complete. Implement RN host grant as a separate native slice with its own RED/real-device proof.
5. Dynamic acceptance requires staging deployment with authenticated service identities and fixed, independently attested staging build pins/audience, actual classified Go→Coordinator→Registrar→Signer v3 issuance, browser cross-target/recovery/revocation tests, current-selector checks at **every** getter/sign/transport and receiving API admission, and iOS/Android native-build, host signout/key-use/device tests. Compare deployed package/bundle/native/image identities to the approved manifest and prove staging/production trust profiles cannot be switched by runtime config. Any missing proof keeps C5, G5/G6, and C7 blocked.

Useful bounded source commands, from each owning worktree, are `go test ./internal/authproxy/...` in Services `go/`; `cargo +1.94.1 test --offline --locked -p coordinator --lib <focused-filter>` and `-p registrar` in Services; `cargo +1.94.1 test --offline --locked -p signer --lib <focused-filter>` in Enclave; and in SDK-JS `C5_TARGET_CLAIM_RED=1 node packages/core/src/__tests__/browser/web-bound-oauth-optin.cjs`, the same command without the RED flag, `node packages/core/src/__tests__/browser/mixed-core-bound.red.cjs`, `pnpm --filter @0xkey-io/core typecheck`, and `pnpm --dir examples/authentication/captcha-rn-expo test:native-bound-context`. Select actual focused Rust test filters from tests added in each slice; these commands are not evidence that those tests or PostgreSQL/device gates have run.

**Stop immediately** if the implementation would infer currentness from a historical signature or a non-atomic RPC read, accept untrusted self-report as parent/config/nonce authority, join holder and OIDC proofs by a caller-chosen ID, issue a new `jti` on an ambiguous same-operation retry, add a key from JWT/response data, let v3 fall back to legacy/fetched claims-only behavior, expose a JS path that can mint a native grant, or permit offline/stale client or server use. Such a design needs a revised contract and review before any opt-in or staging use.
